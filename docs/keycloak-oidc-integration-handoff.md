# 키클락(Keycloak) 연동 요청서 — 사후관리 심사 웹서비스 ↔ 인프라팀

> **이 문서의 목적**: JB우리캐피탈 질권담보 대출심사 웹서비스(`newtech-platform`)의 **로그인·권한·담당자 표시**를
> 사내 키클락(AD/LDAP 페더레이션)에 연동하기 위해, **인프라팀이 키클락에서 설정해 주실 항목**과
> **앱팀에 돌려주셔야 할 값**을 정리한 요청서입니다. 앱팀이 답하는 문서가 아니라 인프라팀이 채워주시는 문서입니다.
>
> 대상 독자: 사내 인프라/IAM(키클락 운영) 담당자. 작성: 앱팀.

---

## 0. 한 줄 요약

앱은 **자체 ID/비밀번호 로그인을 키클락 OIDC 로그인으로 교체**하려 합니다. 인프라팀은 (1) 이 앱용 **키클락 client** 하나를 만들어 주시고, (2) **LDAP 그룹 → 권한(역할)** 매핑과 (3) **사번(employeeNumber)을 토큰에 포함**되게 설정해 주신 뒤, (4) 아래 §3 체크리스트의 값들을 앱팀에 전달해 주시면 됩니다.

---

## 1. 배경 (왜 필요한가)

- 앱은 심사역·관리자가 쓰는 내부 웹서비스(React SPA + FastAPI API)입니다. 현재는 앱 자체 계정(ID/비번)으로 로그인합니다.
- 사내 표준이 **키클락 SSO**로 정해져, 앱 로그인도 키클락으로 통일하려 합니다.
- 특히 **사후관리 모니터링 화면**에서 각 대출의 **담당자(여신담당)** 를 표시해야 하는데, 대출 데이터에는 담당자가 **사번(`employeeNumber`)** 으로 들어 있습니다.
- **현 디렉터리(키클락+LDAP)는 사용자 속성이 이메일·사번뿐, 이름(displayName)은 없음** → 담당자는 **사번 그대로 표시**합니다(사번→이름 변환은 불필요·불가). 이름 속성이 추후 디렉터리에 추가되면 그때 이름 표시로 확장.
- 업무 규칙: **로그인하는 현업과 그 대출을 실행한 여신담당은 동일인**이어야 합니다 → 로그인 신원(사번)과 대출의 담당 사번이 같은 디렉터리에서 나와야 일치가 보장됩니다.

---

## 2. 인프라팀에 요청하는 키클락 설정 (3가지)

### 2-1. 이 앱용 OIDC client 생성
- 로그인 방식: **Authorization Code + PKCE** (SPA 표준). 사용자가 키클락 로그인 페이지로 갔다가 앱으로 돌아오는 방식.
- client 유형: **public**(SPA) 권장. (백엔드 confidential 별도 필요 시 §5-B 참고)
- 등록할 **Redirect URI / Web Origin** (앱 접속 주소):
  - 운영: `http://100.114.93.58:5173/*`
  - (개발/검증용도 함께 필요 시) `http://100.114.93.58:5180/*`, `http://localhost:5173/*`
  - 운영 도메인이 별도로 잡히면 그 주소도 추가
- 토큰에 다음 클레임 포함: `preferred_username`, `email`, 사번(§2-3). (이름 속성은 디렉터리에 없음)

### 2-2. 권한(역할) 매핑 — LDAP 그룹 → 키클락 역할
- 앱은 **두 역할**만 구분합니다: **관리자(admin)** / **심사역(auditor)**. (그 외는 접근 불가)
- 사내 **LDAP 그룹 멤버십 → 키클락 역할**로 자동 매핑되게 설정해 주세요.
- 토큰에서 역할이 보이도록: **realm role**(`realm_access.roles`) 또는 이 client의 **client role**(`resource_access.<client>.roles`) 중 한 방식으로 노출. (어느 쪽이든 OK — §3에 어느 방식인지만 알려주세요)
- 어떤 LDAP 그룹이 admin이고 auditor인지 매핑표(§3)에 적어주세요.

### 2-3. 사번(employeeNumber)을 토큰 클레임으로 포함 ★중요
- 담당자 표시·본인 대출 필터의 핵심입니다. 각 사용자의 **AD/LDAP `employeeNumber`(사번)** 가 키클락 토큰에 **고정된 클레임 이름**으로 들어오게 해주세요(예: 클레임명 `employee_number`).
- AD 페더레이션이면: AD `employeeNumber` → 키클락 User Attribute → **Protocol Mapper(User Attribute)** 로 토큰에 추가.
- 이게 있어야 "로그인한 사람의 사번"과 "대출의 담당 사번(`LNBZ_CHRG_EMPNO`)"을 맞춰 담당자를 사번으로 표시하고 본인 담당 대출을 필터할 수 있습니다.

### 2-4. (사번→이름 조회) — **불필요**
현 디렉터리에 이름 속성이 없으므로 담당자는 사번으로 표시합니다. 별도 LDAP 읽기 계정/Admin API 제공 **불필요**.
(추후 디렉터리에 이름이 생기고 이름 표시가 필요해지면, 그때 LDAP 읽기 서비스계정 또는 키클락 Admin API 한 가지를 추가로 요청하겠습니다.)

## 3. 인프라팀 → 앱팀 전달 값 (체크리스트)

설정 후 아래를 채워 전달해 주시면 앱팀이 바로 배선합니다.

| 항목 | 값 | 비고 |
|---|---|---|
| 키클락 Issuer URL | `https://<keycloak-host>/realms/<realm>` | OIDC discovery: `.../.well-known/openid-configuration` |
| Realm 이름 | | |
| Client ID | | §2-1에서 만든 것 |
| Client 유형 | public / confidential | confidential이면 client secret도 |
| 로그인 플로우 | Authorization Code + PKCE | |
| JWKS URL | `https://<host>/realms/<realm>/protocol/openid-connect/certs` | 토큰 서명 검증용 |
| 역할 클레임 위치 | `realm_access.roles` 또는 `resource_access.<client>.roles` | 둘 중 어느 쪽 |
| LDAP그룹→역할 매핑 | admin = `<그룹>` / auditor = `<그룹>` | |
| 사번 클레임 이름 | 예: `employee_number` | §2-3, 담당자 표시 키 |
| 이메일 클레임 | `email` | 디렉터리에 이름 속성 없음 → 이메일·사번만 |
| 등록된 Redirect URI | (확인) | §2-1 |

---

## 4. 앱팀이 구현하는 범위 (경계 — 인프라팀이 안 하셔도 되는 것)

인프라팀은 키클락 설정 + 위 값 전달까지면 됩니다. 아래는 **앱팀 몫**:
- 프론트(SPA)에서 키클락 로그인 리다이렉트 처리(`keycloak-js`/`oidc-client-ts`).
- API에서 키클락 토큰을 JWKS로 검증, 역할 클레임으로 접근 제어(admin/auditor).
- 대출의 담당 사번(`LNBZ_CHRG_EMPNO`)을 담당자 칼럼에 **사번 그대로** 표시.
- 토큰의 사번으로 심사역은 본인 담당 대출만/관리자는 전체 필터.

---

## 5. 인프라팀이 정해주실 결정 (추천안 포함 — 확인만 해주셔도 됨)

- **A. client는 새로 1개** 만든다(앱 전용). *추천: 신규 client `newtech-platform`.*
- **B. 로그인 플로우**: SPA **Authorization Code + PKCE**(표준·권장). *비권장 대안: ROPC(앱 폼에서 ID/비번 받기) — 키클락이 별도 허용해야 하고 보안상 권장 안 됨.*
- **C. 담당자 표시**: 디렉터리에 이름이 없으므로 **사번 그대로 표시**(추가 조회 경로 불필요). 이름 표시는 디렉터리에 이름 속성이 생긴 뒤로 보류.

---

## 6. 용어 미니 사전 (앱팀↔인프라팀 정렬용)

- **OIDC**: 키클락 같은 SSO가 앱에 "이 사람 누구"임을 토큰으로 알려주는 표준 프로토콜.
- **client**: 키클락에 등록하는 "앱 한 개" 단위. 우리 웹서비스를 위한 client 하나가 필요.
- **claim(클레임)**: 토큰 안에 담기는 사용자 정보 한 조각(이름·역할·사번 등).
- **employeeNumber(사번)**: 담당자 표시·본인대출 매칭의 키. 토큰에 반드시 포함돼야 함(§2-3).
- **JWKS**: 토큰이 진짜 키클락이 발급한 건지 앱이 검증할 때 쓰는 공개키 묶음.
- **realm role / client role**: 키클락의 권한 묶음. 우리는 admin/auditor 두 개만 쓰면 됨.
